# nwsctl apply

Executes the Plan generated by `nwsctl plan` and transitions the infrastructure to the desired state.

```
nwsctl apply --plan <plan-file> [flags]
```

---

## Overview

`nwsctl apply` executes the task DAG described in `plan.json` in order. When a task succeeds, the State is updated, and subsequent `nwsctl plan` runs will treat it as already applied.

---

## Flags

| Flag | Short | Default | Description |
|------|-------|---------|-------------|
| `--plan` | | (required) | Path to the Plan file to execute |
| `--recipe-dir` | | | Path to a Recipe directory (can be specified multiple times) |
| `--work-dir` | | `.niwashi` | Path to the Workspace |
| `--dry-run` | | `off` | Dry-run mode (`off` / `simulate`) |
| `--destroy` | | `false` | Execute a destroy plan (generated with `plan --destroy`) |
| `--prune` | | `false` | Execute a prune plan (generated with `plan --prune`) |
| `--yes` | | `false` | Skip the confirmation prompt for destroy/prune plans (`--destroy` / `--prune`) |
| `--strict-check` | | `false` | Fail if recipes have changed since the plan was created (see below) |

---

## Usage

### Basic Usage

```bash
nwsctl apply --plan plan.json --recipe-dir ./recipes
```

### Dry Run (--dry-run simulate)

```bash
nwsctl apply --plan plan.json --recipe-dir ./recipes --dry-run simulate
```

Runs through the Plan without executing actual operations. Inside Recipe scripts, `NWS_DRY_RUN_ENABLED=1` is set, so Recipes can reference this variable to implement dry-run behavior (such as running only syntax checks).

### Executing Destroy and Prune Plans (--destroy / --prune)

To execute a destroy plan generated by `nwsctl plan --destroy`, you must also specify `--destroy` on `apply`. Similarly, to execute a prune plan generated by `plan --prune`, specify `--prune`. Attempting to apply these plans without the corresponding flag will result in an error.

```bash
# Execute a destroy plan
nwsctl apply --plan plan.json --recipe-dir ./recipes --destroy

# Execute a prune plan
nwsctl apply --plan plan.json --recipe-dir ./recipes --prune
```

In both cases, a confirmation prompt is displayed asking whether it is safe to delete resources. In non-interactive environments such as CI, you can skip it by adding `--yes` (the prompt is not displayed in dry-run mode).

```bash
nwsctl apply --plan plan.json --recipe-dir ./recipes --destroy --yes
```

## Recipe Integrity Check

`nwsctl apply` checks whether the recipes in `--recipe-dir` match the fingerprints recorded in the plan file. This detects cases where a recipe was modified after the plan was created — for example, when a recipe is updated between plan and apply in a CI pipeline.

By default, a mismatch logs a warning and apply proceeds. Add `--strict-check` to treat any mismatch as an error and abort.

```bash
nwsctl apply --plan plan.json --recipe-dir ./recipes --strict-check
```

To apply with updated recipes, re-run `nwsctl plan` to generate a new plan.

## SSH Connection Settings

When `nwsctl apply` connects to instances via SSH, timeout and retry behavior can be tuned with the following environment variables. This is useful when the target environment has slow networks or when cloud VMs take time to become reachable after creation.

| Environment variable | Default | Description |
|----------------------|---------|-------------|
| `NWS_SSH_CONNECT_TIMEOUT_SEC` | `10` | TCP connection timeout in seconds |
| `NWS_SSH_HANDSHAKE_TIMEOUT_SEC` | `10` | SSH handshake timeout in seconds |
| `NWS_SSH_RETRY_MAX_COUNT` | `3` | Number of connection attempts before giving up |
| `NWS_SSH_RETRY_INTERVAL_SEC` | `5` | Interval between retries in seconds |

```bash
NWS_SSH_RETRY_MAX_COUNT=10 NWS_SSH_RETRY_INTERVAL_SEC=10 \
  nwsctl apply --plan plan.json --recipe-dir ./recipes
```
